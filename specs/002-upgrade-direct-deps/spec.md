# Feature Specification: 升级直接依赖至最新版本

**Feature Branch**: `002-upgrade-direct-deps`

**Created**: 2026-11-25

**Status**: Draft

**Input**: User description: "检查相关直接依赖， 升级到最新版本"

## Clarifications

### Session 2026-11-25

- Q: 当某个直接依赖的最新版本需要修改本项目自己的源代码才能通过构建和验收时，这次升级是否应该包含这些源代码改动？ → A: 允许为采用最新版本做必要的少量源码适配，前提是全部既有验收门禁仍通过、支持边界不变。

## User Scenarios & Testing *(mandatory)*

<!--
  User stories are prioritized as user journeys ordered by importance.
  Each story is independently testable and delivers value on its own.
-->

### User Story 1 - 盘点直接依赖并识别可升级项 (Priority: P1)

作为项目维护者，我想要清楚知道项目当前声明了哪些直接依赖、各自处于什么版本，以及其中哪些存在更新的可用版本，这样我才能在不破坏已验收行为的前提下判断升级范围。

**Why this priority**: 没有准确的现状盘点，任何升级都是盲目的。这是后续所有决策的前提，也是最高价值的可独立交付成果。

**Independent Test**: 仅执行本故事即可产出一份完整的依赖清单，其中包含每个直接依赖的当前版本与升级结论，无需改动任何依赖即可验收。

**Acceptance Scenarios**:

1. **Given** 项目处于当前已验收状态，**When** 维护者检查已声明的直接依赖，**Then** 得到一份覆盖全部直接依赖的清单，且每项都记录当前版本与是否有更新可用。
2. **Given** 某个直接依赖存在更新版本，**When** 维护者评估其兼容性，**Then** 清单中明确记录该依赖是否可升级以及判定依据。
3. **Given** 某个直接依赖没有任何更新版本，或仅有与当前工具链不兼容的更新版本，**When** 完成评估，**Then** 该项被明确记录为"保持原样"及原因，而非被遗漏。

---

### User Story 2 - 将兼容的直接依赖升级至最新版本 (Priority: P1)

作为项目维护者，我想要把每一项可升级的直接依赖提升到与当前工具链兼容的最新版本，以便及时获得缺陷修复与安全改进，同时不引入浮动版本。

**Why this priority**: 这是用户请求的核心价值——"升级到最新版本"。盘点只在升级落地后才产生实际收益。

**Independent Test**: 可在故事 1 的清单基础上独立完成——对清单中每一项"可升级"依赖执行升级，并确认依赖声明中不再存在浮动版本引用。

**Acceptance Scenarios**:

1. **Given** 某直接依赖存在兼容的最新版本，**When** 执行升级，**Then** 该依赖被更新到该最新版本，并带有精确锁定的版本标识与内容哈希。
2. **Given** 升级涉及依赖声明的改动，**When** 检查改动结果，**Then** 所有直接依赖仍使用精确版本/提交与固定哈希，不存在浮动版本或占位引用。
3. **Given** 某依赖的最新版本与当前工具链不兼容，**When** 执行升级决策，**Then** 该依赖保持原样并记录原因，工具链版本未被修改或放宽。
4. **Given** 全部升级完成，**When** 从干净状态构建，**Then** 构建成功且不依赖运行时网络访问。

---

### User Story 3 - 验证升级后无回归并留痕 (Priority: P2)

作为项目维护者，我想要确认升级没有破坏任何已验收行为，并且升级结论可被追溯，这样后续维护者才能理解每一项升级的决策依据。

**Why this priority**: 本项目的验收结论是受保护基线；没有验证与记录的升级会把回归风险悄悄带入工程。

**Independent Test**: 可在升级完成后独立执行全部验收门禁并审阅记录文档，确认零新增失败项。

**Acceptance Scenarios**:

1. **Given** 依赖升级已完成，**When** 运行全部既有验收门禁，**Then** 所有门禁通过，且无新增失败项。
2. **Given** 两个基础演示模式，**When** 分别构建与测试，**Then** 二者均保持可独立构建和测试，不因升级而依赖此前被跳过的集成模块。
3. **Given** 升级已完成，**When** 审阅项目文档，**Then** 每个被评估的依赖都有"原版本 → 新版本（或保持原样）"的记录及理由。

---

### Edge Cases

- 某依赖的最新版本要求更高版本的构建工具链，而工具链被项目规则精确锁定：该依赖保持原样，记录"工具链不兼容"，不得为此修改或放宽工具链版本校验。
- 某依赖升级后引入不兼容的 API 变化，导致验收门禁失败：允许为采用最新版本做必要的少量源码适配，前提是全部既有验收门禁仍通过且支持边界不变；若适配无法满足该前提，则回退该依赖至最后一个通过全部门禁的版本并记录原因；不得以降低验收标准来迁就升级。
- 某依赖是按提交哈希固定的分支/分叉，不存在传统"版本号"：以该来源上最新且通过全部验收门禁的提交作为其"最新版本"。
- 升级后干净环境的离线构建失败：定位导致失败的依赖并回退，直到离线构建重新通过。
- 检查最新版本期间网络不可用：记录该情况并推迟升级决策，不得猜测版本或引入浮动引用。

## Requirements *(mandatory)*

<!--
  Requirements are testable and avoid prescribing how to implement.
-->

### Functional Requirements

- **FR-001**: 系统 MUST 枚举项目依赖清单中声明的全部直接依赖，不遗漏任何一项。
- **FR-002**: 系统 MUST 为每一项直接依赖判定是否存在更新版本，以及该更新版本是否与当前锁定的工具链和全部验收门禁兼容。
- **FR-003**: 系统 MUST 将每一项判定为"可升级"的直接依赖更新到其兼容的最新版本，并保持精确锁定的版本标识与内容哈希。
- **FR-004**: 系统 MUST NOT 在依赖声明中引入浮动版本、通配符版本或未固定的引用。
- **FR-005**: 系统 MUST NOT 修改或放宽被项目规则精确锁定的构建工具链版本及其校验。
- **FR-006**: 对于无兼容更新版本的直接依赖，系统 MUST 保持其原样并记录判定原因。
- **FR-007**: 升级完成后，系统 MUST 通过全部既有验收门禁，包括核心测试、物理测试，以及两个基础演示模式的独立构建与测试，且无新增失败项。
- **FR-008**: 升级完成后，系统 MUST 能在无网络访问的干净环境中成功构建。
- **FR-009**: 系统 MUST 在项目文档中记录每个直接依赖的评估结果，包括原版本、新版本（或"保持原样"）及理由。
- **FR-010**: 升级 MUST 保持增量性，不得改变已记录在文档中的支持边界、物理与相机不变量，以及已验收的缓存语义。
- **FR-011**: 当最新版本需要源码适配时，系统 MUST 仅进行为采用该版本所必需的最小改动，且改动后全部既有验收门禁仍通过、已记录的支持边界与不变量不变；若无法满足，则 MUST 回退该依赖并记录原因。

### Key Entities *(include if feature involves data)*

- **直接依赖 (Direct Dependency)**: 项目依赖清单中显式声明的一项外部组件；关键属性包括名称、当前版本/提交、内容哈希、可用的最新版本、兼容性判定与最终升级结论。
- **验收门禁 (Acceptance Gate)**: 一套既有且必须全部通过的检查；关键属性包括检查范围与通过/失败结果。本功能涉及的核心门禁为：核心测试、物理测试、两个基础演示模式的独立构建与测试、离线干净构建。
- **升级记录 (Upgrade Record)**: 针对每个直接依赖的追溯条目；关键属性包括原版本、新版本（或"保持原样"）、兼容性判定理由。

## Success Criteria *(mandatory)*

<!--
  Measurable, technology-agnostic, user-focused, verifiable outcomes.
-->

### Measurable Outcomes

- **SC-001**: 100% 的已声明直接依赖都完成了评估，且每一项都有明确的升级或保持原样的结论，无遗漏项。
- **SC-002**: 所有存在兼容更新版本的直接依赖中，100% 被更新到该最新版本；依赖声明中浮动版本引用的数量为 0。
- **SC-003**: 升级后全部既有验收门禁中，通过率为 100%，新增失败项数量为 0。
- **SC-004**: 升级后从干净状态发起的离线构建成功率为 100%（无需网络访问）。
- **SC-005**: 被锁定的构建工具链版本在整个过程中保持不变，放宽校验的改动数量为 0。
- **SC-006**: 100% 的被评估依赖都在项目文档中有可追溯的升级记录（原版本、新版本及理由）。

## Assumptions

- "相关直接依赖"指项目依赖清单中显式声明的直接依赖；构建工具链本身不在升级范围内，因为项目规则对其进行了精确锁定。
- "最新版本"指与当前锁定工具链兼容、且能通过全部验收门禁的最新稳定版本/提交；仅存在"更新但不兼容"版本时，视为无可用升级。
- 精确版本与内容哈希锁定的规则在升级后继续有效；不得为升级目的引入浮动版本。
- 检查与获取最新版本期间允许联网，但升级完成后必须脱离网络也能干净构建。
- 升级允许为采用最新版本做必要的少量源码适配，但不得借机扩展功能或改变已记录的支持边界、物理/相机不变量与缓存语义；若适配后无法通过全部门禁，则回退该依赖。
- 项目文档语言保持中文；标识符、命令与路径保持英文。
